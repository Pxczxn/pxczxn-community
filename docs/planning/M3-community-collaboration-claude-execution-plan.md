# M3 团队博客、协作创作与社区化界面执行计划

> 用途：将本文件逐项交给 Claude Code 执行。一次只执行一个任务；完成后必须停下，等待 Reviewer 审查、运行门禁并创建下一任务。
>
> 当前稳定基线：`M3-dev` 的 `bdc301a`（团队模型与权限地基已合并）。`feature/m3-t002-team-application` 中未提交的试验性改动不是基线，必须先清理或从 `M3-dev` 新建任务分支。

## 0. 总规则

1. 星语社区是博客社区，用户端服务发现、阅读、创作、互动与个人/团队博客；管理端服务运营、审核、治理、用户与博客管理。
2. 不把组织、岗位、部门、OA、审批流等企业管理语义放入社区核心导航；平台内部人员权限仍可复用脚手架 `sys_role`，但团队 `OWNER/ADMIN/EDITOR/AUTHOR` 永远只存在于团队领域。
3. 每个任务单独分支、单独 commit、单独 worktree；只修改本任务允许范围。禁止改已发布迁移。
4. MySQL 是业务事实来源。写操作必须具备资源级鉴权、幂等、条件更新/乐观锁、事务和不可变审计。Redis 只能优化。
5. 每个新 `Vxxx` 迁移都必须有同版本 `database/verify/Vxxx__verify_*.sql` 和 `database/rollback/Rxxx__rollback_*.sql`；verify/rollback 不得放进 migrations 目录。
6. 不得用静态假团队、假成员、假统计或硬编码审批记录替代真实 API。未交付功能必须是明确的空状态，不能伪装完成。
7. 不得用 `any`、关闭类型检查、忽略错误或删除测试通过门禁。

## 2. 任务顺序

### M3-T002：团队申请与平台审核

**目标**：社区用户申请团队；平台运营审核；仅审核通过时在同一事务创建 `TEAM` blog、`team`、OWNER 成员、默认 setting/分类及审计事件，并通知申请人。

**允许范围**：团队应用服务与 mapper、web/admin API、V024、博客端申请/状态页、管理端真实审核队列、测试。

**关键规则**：

- 校验用户状态、slug、重复有效申请与 idempotency key。
- 查询/撤销仅限申请人；平台审核仅限既有 `community:team:review` 权限。
- 审批采用状态条件更新；并发审批只有一个成功；拒绝和撤销绝不创建 team/blog。
- 不得在注册时自动创建团队；不实现邀请、工作台、投稿或共创。

**验收**：重复提交、相同幂等键、撤销、拒绝、并发审批、无审核权限 403、成功后的原子创建与通知；后端+博客端+管理端的测试、typecheck、lint、build 全通过。

### M3-T003：团队成员、邀请与 Owner 转让 API

**目标**：建立邀请、接受/拒绝、退出、移除、角色调整、Owner 转让、解散等真实 API 与审计。

**关键规则**：

- 邀请 token 只保存哈希；同一有效邀请幂等。
- OWNER 可管理所有角色；ADMIN 只可管理 EDITOR/AUTHOR；EDITOR/AUTHOR 不能管理成员。
- Owner 转让复用 `TeamAuthorityService`；不能出现零 OWNER 或双 OWNER。
- 所有团队 ID、成员 ID 必须服务端验证归属；跨团队为 403/404，不泄露数据。

**验收**：邀请幂等、接受/拒绝、退出、移除越权、角色调整越权、Owner 权限回收、解散后只读与审计测试通过。

### M3-T004：团队主页与团队工作台

**目标**：交付 `/teams`、`/teams/{teamSlug}`、`/workspace/teams/{teamId}` 的真实页面和 API，不再显示 M3 占位页。

**范围**：团队资料、公开文章、成员展示、团队动态、分类、工作台概览/成员/文章/分类/设置；管理端团队治理只读和审计查询。

**UI 规则**：使用团队原型的封面、身份区、内容流、侧栏、工作台 KPI/待办/成员结构，但只呈现 API 返回的真实数据；AUTHOR 不显示成员管理和团队设置；Loading、Empty、Error 必须完整。

**验收**：成员仅见所属团队；篡改 teamId/slug 不泄露；冻结/解散只读；每项写操作写审计；博客端和管理端三色主题可用。

### M3-T005：外部投稿与双层审核

**目标**：实现不可变 `team_submission`：个人文章固定版本投递到团队，团队审核后进入平台审核，最后创建团队博客下的发布文章。

**关键规则**：

- 投稿固定 `article_version`，原文后续修改不污染已投递版本。
- 一篇个人 article 不直接改归属；最终发布创建团队博客文章，保留原作者和投稿关系。
- 状态机：`SUBMITTED → TEAM_REVIEWING → TEAM_APPROVED → PLATFORM_REVIEWING → PUBLISHED`，并支持退修、拒绝、撤稿。
- 每次状态改变使用条件更新/乐观锁、事务、审计与通知。

**验收**：重复投递、撤稿、团队退修/拒绝、平台拒绝、跨团队审核越权、并发领取、最终发布和原作者归属 E2E。

### M3-T006：文章共创

**目标**：实现文章范围的协作邀请、接受/拒绝、贡献类型、署名顺序与审计。

**关键规则**：

- 不能复用 `team_invitation`；协作授权只作用于单篇文章。
- 共创者默认只有署名/展示权，不自动获得编辑、发布、删除、审核、收益或团队管理权。
- 若给予编辑权，必须显式、可撤销、文章范围内；不复制正文、版本、评论或互动数据。

**UI**：采用共创原型的成员清单、协作约定、邀请与版本记录，但权限按钮由 API 返回的能力决定。

**验收**：邀请幂等、接受/拒绝、撤销、排序冲突、无权编辑/发布、退出团队后的展示策略及公开署名。

### M3-T007：社区用户即时聊天

**目标**：将现有平台聊天能力扩展为符合社区用户端语义的真实聊天入口与页面。

**关键规则**：

- 复用已完成的短时单次 WebSocket ticket 和聊天治理能力；握手不接收 URL token。
- 只允许已授权的会话/群组成员读写；跨用户、跨团队、被治理用户都必须被拒绝。
- 聊天页面使用原型的通知/聊天入口语义，不使用内部办公消息、组织通讯录或 OA 词汇。

**验收**：401、403、跨会话访问、重复 ticket、消息发送/已读/错误/空状态、浅色/深色/星空主题与浏览器 E2E。

### M3-T008：全站社区化文案与首页/发现页收口

**目标**：以两份原型图为参考，收口博客端、管理端与可见错误/空状态中的产品文案和信息架构。

**范围**：仅用户可见社区页面、导航、标题、空状态、按钮、管理端一级菜单及说明文案；不机械替换第三方版权、历史 ADR 或系统底层术语。

**验收**：扫描用户端/管理端主要路由无“公司、部门、岗位、组织架构、OA、员工管理”等错误产品语义；保留“平台人员/权限”只在系统设置内；首页、发现、团队、聊天、审核页面均使用真实数据或诚实空状态。
