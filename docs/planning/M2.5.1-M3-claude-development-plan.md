> 用途：这是交给 Claude 的实施任务书，也是后续 Code Review 和测试的唯一验收基线。

## 1. 已确认的项目现状

- 仓库由 `pxczxn-backend`（Java 21 / Spring Boot / Maven）、`pxczxn-web`（React 19 / vinext）和 `pxczxn-admin`（Vue 3 / Vite）组成；数据库迁移位于 `database/migrations`，每个迁移必须有同版本 `database/verify` 脚本。
- 顶层 Maven 模块、数据库运行名和绝大多数平台包已完成改名：运行数据库是 `pxczxn_community`，主包是 `top.pxczxn.platform`。
- 仍有实际 Mars 遗留：未接入 reactor 的 `mars-biz`、`mars-web-api`、`mars-app-api` 目录及其 `com.mars` 源码；历史 ADR/验收文档中也保留了来源说明。前者必须清理；后者只能更新为“迁移历史”，不能篡改历史事实或第三方版权文本。
- 生产安全项已经部分修复，必须做回归验证而非推翻重做：生产 CORS 读取 `PXCZXN_CORS_ALLOWED_ORIGINS`，`demo-mode=false`，日志为 INFO，WebSocket 已使用 30 秒、一次性 ticket 并在生产要求 Redis，Druid 生产凭据来自环境变量，服务端没有固定 `123456`。
- 仍未解决的公开网页风险是用户会话写入 `pxczxn-web/app/lib/community-api.ts` 的 `localStorage`；管理端的 Pinia 持久化也保存 token。仅改前端存储不够，必须和后端认证/CORS/CSRF 策略一起设计和测试。
- M3 的可复用地基已存在：`blog` 支持 `PERSONAL`/`TEAM`；`article`、`article_version` 和 `content_review_task` 已支持固定审核版本和 `TEAM_INTERNAL` 审核阶段；文章权限提供 `BlogArticleRoleResolver` 扩展点，评论可通过 `TeamBlogMemberResolver` 扩展成员判断。

## 2. 总体规则（Claude 必须遵守）

1. 先阅读本文件、`docs/delivery/M2.5-M6-task-breakdown.md`、相关现有测试及迁移；不要用静态假数据替代真实业务。
2. 一次只做一个阶段/任务。每次开始前列出将修改的文件；完成后运行该任务的测试和完整质量门禁。不要顺带格式化无关文件。
3. 后端业务放在 `top.pxczxn.community.<domain>`，平台脚手架放在 `top.pxczxn.platform`；不得新建 `com.mars`、不得把团队角色写入 `sys_role`、不得让 Controller 承担角色判断。
4. MySQL 是事实来源。所有写操作必须做资源级鉴权、幂等处理、事务边界和不可变审计；Redis 只能加速，Redis 不可用不能丢失团队、投稿或审核事实。
5. 不修改已发布迁移。每个新 `Vxxx` 迁移必须配套同号 `verify/Vxxx__verify_*.sql`；提供对应 rollback 脚本。迁移编号从仓库当前最大版本的下一个版本连续递增。
6. 所有 API 在网页端、管理端和权限测试中同时落地；禁止只做页面、只做 Mapper 或只做接口声明。
7. 每个阶段结束时更新交付记录，说明 API、表、状态机、测试命令和结果；失败不能写“完成”。

### 0.2 M2.5.1-T002：生产安全债回归与补齐（独立 commit）

先基于 `scripts/verify-security.ps1` 的已有断言做真实回归，再只修复仍存在的缺口。

| 项目 | 实施要求 | 验收要求 |
| --- | --- | --- |
| CORS | 生产环境只接受显式 `PXCZXN_CORS_ALLOWED_ORIGINS`；无值时启动失败或拒绝跨域，不能降级为 `*`；凭据请求不得使用通配符。 | 允许源预检成功，攻击源无 `Access-Control-Allow-Origin` 且为 4xx。 |
| 管理员密码 | 生产绝不创建/重置 `123456`；本地演示密码只能在 local profile 且有醒目说明。 | 源码与种子数据扫描无生产固定口令；首次初始化使用环境变量或一次性随机密码并要求修改。 |
| WebSocket | 保持 opaque、短时、单次 ticket；握手不得接收 `token` URL 参数，生产无 Redis 时拒绝签发。 | ticket 第二次使用失败；`?token=` 的握手被拒绝；日志不输出凭据。 |
| demo / debug | 生产 `demo-mode=false`、根日志 INFO 或更高；Actuator 只暴露必要健康信息。 | prod 配置和启动后的 `/actuator` 均符合最小暴露。 |
| Druid | 生产禁用 Druid web console；如必须启用，仅内网/管理网络 + 强密码 + 明确 allowlist，绝不能默认暴露。管理端菜单与后端暴露策略一致。 | 外网/普通社区会话访问 `/druid/**` 为 404/403；无默认账号。 |
| 浏览器 token | 制定并实现同站会话迁移：推荐 `Secure; HttpOnly; SameSite=Lax/Strict` cookie，前端不再读取/持久化 bearer token。若前后端跨站部署，需同时增加 CSRF token 双提交或等效保护、精确 CORS 和凭据策略。迁移期需支持旧会话一次性失效/重新登录。 | 网页端和管理端 localStorage/sessionStorage/Pinia 持久化中没有认证 token；登录、刷新、退出、401、跨源请求、CSRF 攻击均有自动化测试。 |

> 注意：cookie 认证会影响现有 `Authorization` 传递方式和 WebSocket ticket 签发接口。先写 ADR，明确部署域名、cookie Domain、SameSite 和 CSRF 方案，再改代码；没有该 ADR 不得直接把 token “换个地方存”。

## 5. 阶段 1：M3 团队协作（数据库和权限先行）

### M3-T001：团队模型与权限地基（不做页面）

本任务只交付数据库、领域模型、权限引擎、内部/API 契约和测试，不实现工作台视觉页面。

#### 必需数据模型

用户给出的六表是核心，但要支持“申请后才创建团队”，还必须增加 `team_application`。建议 schema：

| 表 | 关键字段和约束 |
| --- | --- |
| `team` | `id`、唯一 `blog_id`（FK `blog`）、`owner_user_id`、`status`、`created_at`、`updated_at`、`lock_version`；关联博客必须 `blog_type='TEAM'`，团队解散不物理删除业务审计。 |
| `team_member` | `team_id` + `user_id` 唯一；`role_code`、加入/退出时间、`invited_by_user_id`、乐观锁；活动成员与已退出成员查询可区分。 |
| `team_invitation` | `team_id`、受邀用户、邀请人、目标角色、随机 token 的**哈希**、状态、失效/接受/拒绝时间、幂等键；同一成员/角色的有效邀请唯一。 |
| `team_role` | 固定系统角色 `OWNER`、`ADMIN`、`EDITOR`、`AUTHOR`，含排序与不可删除标记；不是 `sys_role`，前端不能自定义高权限角色。 |
| `team_permission` | 以 `(role_code, permission_code)` 为主键的固定映射（例如成员管理、内容编辑、团队设置、投稿审核、发布），避免没有角色-权限关联的空目录表。 |
| `team_audit_event` | append-only：团队、actor、事件类型、对象类型/ID、请求关联 ID、前后快照 JSON、发生时间；应用账号不得 UPDATE/DELETE 历史。 |
| `team_application` | 申请人、拟用团队名/slug/简介、资料 JSON、状态 `PENDING/APPROVED/REJECTED/CANCELLED`、管理员、原因、审核时间、幂等键；同一用户同时只能有一条有效申请。 |

#### 权限矩阵（最低要求）

| 动作 | OWNER | ADMIN | EDITOR | AUTHOR |
| --- | --- | --- | --- |
| 查看团队内容/成员 | 是 | 是 | 是 | 是 |
| 邀请、移除成员、调整角色 | 是 | 可管理 EDITOR/AUTHOR，不能管理 OWNER/ADMIN | 否 | 否 |
| 转让 OWNER、解散团队、修改关键设置 | 是 | 否 | 否 | 否 |
| 创建/编辑任意团队文章 | 是 | 是 | 是 | 仅自己创建的文章 |
| 删除/发布团队文章 | 是 | 是（发布按业务配置） | 否/不可越权 | 否 |
| 审核外部投稿 | 是 | 是 | 可配置为是 | 否 |

实现要求：新增 `TeamBlogArticleRoleResolver` 和 `TeamBlogMemberResolver` 实现既有扩展点；在一个可单测的 `TeamAuthorityService` 中集中资源级决策。Controller 只能调用该服务。Owner 转让必须在同一事务内校验新 Owner 是活动成员、更新 `team.owner_user_id`、成员角色和关联 team blog 的 owner，并写两条审计事件；永远不允许零 Owner 或双 Owner。

验收：MySQL 迁移/verify、角色矩阵单测、跨团队 403、AUTHOR 编辑他人 403、EDITOR 管成员 403、Owner 转让原 Owner 权限回收、评论 `TEAM_MEMBERS` 真实解析均通过。

### M3-T002：团队申请与平台审核

流程严格为：用户申请 → 状态查询/撤销 → 平台管理员审核 → **同一事务**创建 team blog + team + OWNER 成员 + 默认设置/分类 + 审计事件 → 通知申请人。

- 申请时校验用户状态、slug、重复有效申请和幂等键；审核接口只能由平台 `community:team:review` 权限调用，平台权限继续使用现有 `sys_role`/菜单 RBAC。
- 审批通过时只消费一次申请；并发审批必须仅有一个成功。拒绝必须记录原因，不能创建团队。
- 博客端实现申请表、我的申请状态；管理端实现真实审批队列和详情，不显示虚构团队。

验收：重复提交、并发审批、拒绝、撤销、跨管理员权限和“通过后才可访问团队工作台”E2E 通过。

### M3-T003：团队工作台

路由使用既有方向 `/workspace/teams/{teamId}`，不要继续使用旧的硬编码 `/workspace/team`。实现“我的团队”、概览、成员、文章、分类、投稿、设置；菜单和 API 按 `TeamAuthorityService` 收敛。

- 分类复用现有 `blog_category`，团队文章复用现有文章/版本服务；不得复制一套分类或文章表。
- 每个资源查询必须带 `team_id/blog_id` 归属条件，不能只依赖前端隐藏菜单。
- 管理端的团队治理页面接入真实查询、冻结/解散后的只读展示和审计查询。

验收：成员只能看到所在团队；AUTHOR 看不到成员管理和团队设置；篡改 URL/teamId 不泄漏数据；成员、文章、分类和设置更新有审计。

### M3-T004：外部投稿与双层审核

投稿不能直接修改原文章归属。增加 `team_submission`（每次投递一条不可变记录，含 `source_article_id`、`fixed_source_version_id`、`target_team_id`、状态、审计链、`published_team_article_id`、幂等键；退修后重新提交创建新记录并链接 `supersedes_submission_id`）。

状态机：

```text
SUBMITTED → TEAM_REVIEWING → TEAM_APPROVED → PLATFORM_REVIEWING → PUBLISHED
                 ├→ TEAM_REVISION_REQUIRED / TEAM_REJECTED
                 └→ CANCELLED
PLATFORM_REVIEWING ─→ PLATFORM_REVISION_REQUIRED / PLATFORM_REJECTED
```

- 固定来源 `article_version`；源文章后续编辑不影响当前投稿。
- 团队通过后创建/复用 `content_review_task` 的平台阶段；平台通过时依据固定快照创建团队博客下的发布文章，保留原作者 ID 和投稿关系。不要让同一篇 `article` 同时归属于个人博客和团队博客。
- 所有状态迁移采用条件更新/乐观锁和事务；团队审核人、平台审核人、原因与时间写入审计和通知。

验收：固定版本、重复提交、撤稿、团队退修、团队拒绝、平台拒绝、跨团队审核越权、并发领取/审核、最终团队发布及原作者归属 E2E 全部通过。

### M3-T005：文章共创（最后做）

只在投稿系统稳定后开始。新增文章范围的协作邀请/贡献关系（不能复用 `team_invitation`）：邀请、接受/拒绝、贡献类型、署名排序和不可变审计。

- 共创者默认仅获得署名/展示权；不自动获得编辑、删除、审核、发布、收益或团队管理权。
- 如产品决定给予编辑权，必须是显式、可撤销、文章范围内的授权，不能提升为团队角色。
- 同一文章不复制正文、版本、评论或互动数据；公开页按稳定排序显示贡献者。

验收：邀请幂等、接受/拒绝、撤销、排序冲突、无权编辑/发布、团队退出后展示策略及既有文章数据不复制均有单测和真实 E2E。

## 7. Reviewer（Codex）检查清单

- 先审提交边界：命名清理、安全、CI 与 M3 是否混在一个 commit；禁止越权的无关重构。
- 审 DDL：外键、唯一索引、幂等键、状态约束、并发条件、审计不可变性和 rollback 是否完整。
- 审授权：服务端是否对每个 teamId/articleId/submissionId 做归属和角色校验；平台 RBAC 与团队 RBAC 是否隔离；是否可通过请求体/路径篡改越权。
- 审工作流：每个状态只能按允许迁移，固定版本不可被后续编辑污染，失败事务不产生半个团队或半次发布。
- 跑 Maven、两个前端的 typecheck/lint/test/build、迁移验证、针对本任务的 E2E，以及既有 M2/M2.5 回归；CI workflow 还会检查干净 runner 的可复现性。
