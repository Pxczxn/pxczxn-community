# 星语社区 M2.5-M6 交付规划

> 规划日期：2026-07-27  
> 当前基线：V1（M1 + M2）、即时聊天和 M2.5 已完成验收。
> M3-M6 仍为后续交付规划；M2.5 的实际结果见 `docs/delivery/M2.5-acceptance.md`。

## 1. 路线目标

后续路线不再把原型页当作产品能力。先通过 M2.5 校正平台入口、信息架构和管理端语义，再逐步完成团队协作、平台治理、发现增长及公网运营能力。

```text
当前 V1
  → M2.5 产品语义与入口修正
  → M3 团队博客、投稿、系列、共创
  → M4 举报、屏蔽、申诉、处罚与风控
  → M5 搜索、发现、SEO、RSS、统计与性能
  → M6 生产部署、监控、备份与灰度开放
```

## 2. 共同交付约束

- 每一任务先完成需求、接口和数据设计，再开发后端、博客端、管理端。
- MySQL 是唯一业务事实来源；Redis 只可作为可失效缓存或单机增强。
- 不引入微服务、MQ、Elasticsearch、Flyway 或 Liquibase。M5 搜索先使用 MySQL；数据证明必要时才评估 OpenSearch。
- 团队业务角色与平台 `sys_role` / 管理员 RBAC 严格隔离。
- 所有写操作必须有资源级权限、幂等策略、审计记录和可重复迁移。
- 每阶段结束必须通过后端测试、双前端检查、数据库迁移校验、关键真实 E2E、交付文档与独立 Git 提交。

## 3. 阶段边界与依赖

| 阶段 | 核心目标 | 前置 | 完成后用户可见结果 |
| --- | --- | --- | --- |
| M2.5 | 已完成：校正首页、发现、导航、动态路由及管理端信息架构 | V1 | 首次打开是有真实内容流的博客社区，管理端是运营中心 |
| M3 | 团队、投稿、系列、联合创作 | M2.5 | 团队可以受控创作、协作和发布 |
| M4 | 举报、屏蔽、申诉、处罚、反滥用 | M3 | 用户与运营人员拥有完整治理闭环 |
| M5 | 搜索、可解释发现、SEO、RSS、统计、性能 | M4 | 内容可被发现、订阅和度量 |
| M6 | 生产环境、CI/CD、备份、监控、灰度 | M5 | 可受控地面向公网持续运营 |

## 4. 实施顺序

### 4.1 M2.5 先行

先让已有内容、互动、通知、聊天等真实能力出现在正确入口；不得用硬编码原型路由、静态计数或“智能推荐”文案掩盖尚未实现的能力。

### 4.2 M3 以团队权限为地基

团队申请、成员关系、角色和权限引擎必须先于工作台、投稿、系列、共创页面。每个后续能力都复用团队资源授权，而不是在 Controller 中临时判断角色。

### 4.3 M4 在 M3 后扩展治理对象

举报、处罚、屏蔽和申诉覆盖个人、团队、内容与聊天。任何处罚都必须包含原因、期限、操作者、不可变历史和申诉链路。

### 4.4 M5 保持可解释和可演进

发现排序先使用编辑精选、发布时间、互动热度、关注关系、内容质量和风险状态。不得将规则排序标为 AI 推荐；搜索先用 MySQL 索引和分页。

### 4.5 M6 以可恢复性为发布条件

公网开放前必须完成 HTTPS、环境变量、备份恢复演练、监控告警、发布审批和从邀请用户到公开注册的灰度流程。

## 5. 统一完成定义

一个阶段只有同时满足以下条件才能标记为“完成”：

1. 需求、数据模型、API 契约、权限矩阵和迁移版本已审阅。
2. 后端业务、博客端与管理端都不含仅供演示的关键路径。
3. Maven 测试、博客端 typecheck/lint/test/build、管理端 typecheck/lint/test/build 全部通过。
4. 阶段关键业务存在真实浏览器 E2E；临时测试数据可清理且不污染基线数据。
5. 数据库迁移可重复执行，checksum 与验证 SQL 正常。
6. 开发状态、任务清单、API/页面说明和验收记录同步更新，并形成独立提交。

## 6. M2.5 实施结果

M2.5 已以独立的前后端、数据库迁移和测试改造完成。团队、系列、共创和数据分析保留正式入口，但页面会明确提示对应 M3/M5 尚未交付；不会用静态样例伪装成已上线能力。

后续从 M3-T001 开始，按任务清单顺序独立交付。
